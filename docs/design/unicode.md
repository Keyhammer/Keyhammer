# Unicode: normalisation and a code-point alphabet (issue #19)

Until now the engine compared UTF-8 bytes: `é` was two symbols, a typo on it cost one or
two edits depending on the bytes, and case or accents were the caller's problem. This note
fixes the design before the code: what the new `text` module folds and why, how the search
alphabet moves from bytes to code points without changing a single ASCII result, what that
does to the lower bound, and what is left out. Every decision below is implemented in the
same pull request unless it is listed under "Not done".

## 1. Decisions in one list

1. A new module `keyhammer::text` (`no_std` with `alloc`, no dependencies, no `unsafe`,
   tables of our own) with a `Normalizer` that folds case and, by default, diacritics.
   Terms and queries go through the same function.
2. The search alphabet becomes **Unicode scalar values** (one symbol per code point). A term
   is split into `char`s, a byte query is decoded as UTF-8. For ASCII the symbol is the
   byte, so every ASCII result, cost, id and work counter is unchanged.
3. `Trie::build` does **not** normalise (it keeps today's behaviour for ASCII exactly). The
   new `Trie::build_normalized(items, &Normalizer)` normalises every term and remembers the
   normaliser; the new `Searcher::search_text` / `search_prefix_text` take a `&str` and
   apply the trie's normaliser to it, so terms and queries cannot be folded differently.
4. The class of a symbol for the subtree bound is `s & 63` for ASCII (unchanged) and one of
   the 38 classes that no letter `a`-`z` uses for everything else. The bound stays
   admissible for any class function (section 4).
5. The cost model works on symbols: `sub_cost`, `ins_cost` and `del_cost` accept any
   `Into<u32>` symbol (so `u8` callers still compile). Keys outside `a`-`z` that the
   layouts model now take part in the neighbour relation: `ç` on ABNT2, `ù` on AZERTY,
   `ü`, `ö` and `ä` (added) on QWERTZ, and the punctuation keys of ABNT2, Dvorak and
   Colemak. QWERTY is unchanged. Every other character gets the default costs.
6. Match ranges: only the mapping utilities (`text::SourceMap`, code point to UTF-8 and
   UTF-16 offsets). Highlighting itself is issue #32.
7. Bindings: no code change (only their docs); they still build and pass. What each needs is in
   section 8.

## 2. The `text` module

### 2.1 Pipeline

`Normalizer::normalize(&str) -> String` maps every `char` of the input, in order, through
two optional steps, **diacritics first, then case**:

1. **Diacritic folding** (on by default). A letter of Latin-1 Supplement (U+00C0-U+00FF)
   or Latin Extended-A (U+0100-U+017F) is replaced by its base letter or letters (table
   `BASE`, section 2.2), and a combining mark of the block Combining Diacritical Marks
   (U+0300-U+036F) is dropped. The Latin ligatures U+FB00-U+FB06 (`ﬀ ﬁ ﬂ ﬃ ﬄ ﬅ ﬆ`) are
   expanded to their letters.
2. **Case folding** (on by default). ASCII `A`-`Z`, and the letters of the two blocks,
   are mapped by Unicode full case folding (`CaseFolding.txt`, statuses C and F),
   restricted to those ranges plus `µ` (U+00B5, folds to Greek `μ` U+03BC) and the
   ligatures U+FB00-U+FB06. So `ß` becomes `ss`, `ſ` becomes `s`, `İ` becomes `i` followed
   by U+0307 (combining dot above) and `ŉ` becomes `ʼn` (U+02BC, `n`).

Everything else is copied unchanged: other scripts, digits, punctuation, spaces, NUL,
control characters, zero-width joiners, directional marks and emoji. The output of a
`char` never depends on its neighbours (no context, no locale).

Order matters for two characters. With both steps on, `İ` becomes `I` (the dot is a
diacritic) and then `i`; `ŉ` becomes `'n` and then stays. Running case first would leave
the U+0307 of `İ` and the U+02BC of `ŉ` in front of the diacritic step's tables. With the
order above both steps produce only characters that both steps leave alone, which is what
makes the whole function idempotent (tested exhaustively over every scalar value, all four
flag combinations).

The four combinations are available: `Normalizer::new()` (both on, the default),
`.with_diacritic_folding(false)` (case only: `café` stays `café`, `Café` becomes `café`),
`.with_case_folding(false)`, and both off (identity).

### 2.2 The tables and the policies they encode

The tables are generated by `crates/keyhammer/scripts/gen_text_tables.py` from Python's
`unicodedata` (the Unicode version the script prints) and checked in as Rust source; the
script is only needed to regenerate them. The case table is also checked in the unit tests
against `char::to_lowercase` from `core` (which the tables must agree with except for the
full foldings listed above), so a mistake in the generator would be caught.

`BASE` maps each letter of U+00C0-U+017F to the letters of its NFKD decomposition without
combining marks when that is ASCII (`é` -> `e`, `Ç` -> `C`, `ĳ` -> `ij`, `ſ` -> `s`), and
otherwise to a fixed choice:

| letter | base | why |
| --- | --- | --- |
| `æ` `Æ` | `ae` `AE` | ligature (Danish, Norwegian, old French and English spellings) |
| `œ` `Œ` | `oe` `OE` | ligature (French: `cœur` / `coeur`) |
| `ß` | `ss` | German; also what case folding gives |
| `ø` `Ø`, `đ` `Đ`, `ħ` `Ħ`, `ł` `Ł`, `ŧ` `Ŧ` | `o`, `d`, `h`, `l`, `t` | the stroke is treated as a diacritic |
| `ð` `Ð` | `d` `D` | usual transliteration |
| `þ` `Þ` | `th` `TH` | usual transliteration |
| `ı` (dotless i) | `i` | see Turkish below |
| `ŀ` `Ŀ` | `l` `L` | NFKD gives `l·`; the middle dot is dropped |
| `ĸ` (kra) | `q` | modern Greenlandic spelling |
| `ŋ` `Ŋ` | `n` `N` | no decomposition; the nearest ASCII letter |
| `ŉ` | `'n` | NFKD gives `ʼn`; the apostrophe is made ASCII |

`×` (U+00D7) and `÷` (U+00F7) are not letters and are unchanged.

Consequences, by language (default normaliser):

- **Portuguese, Spanish, French, Italian, Catalan, Romanian, Polish, Czech, Hungarian and
  the rest of Latin Extended-A**: every accented letter meets its base letter. `São Paulo`,
  `sao paulo` and `SÃO PAULO` normalise to `sao paulo`; `ação` to `acao`; `Ç` to `c`.
  The price is that `e` and `é` are the same symbol, so the engine cannot rank `café`
  above `cafe` for the query `café`. The case-only normaliser keeps them apart (then `ç` is
  a symbol of its own and is a neighbouring key of `l` and `p` on ABNT2, section 5).
- **German**: `ß` -> `ss` (so `Straße` = `strasse`), `ä ö ü` -> `a o u`. The German
  convention `ä` -> `ae` is *not* used: it would make `Mueller` and `Müller` equal but
  `Muller` and `Müller` different, and one folding cannot serve both. Case-only keeps the
  umlauts, which are neighbouring keys on QWERTZ.
- **Turkish and Azerbaijani**: there is no locale tailoring. `I` always folds to `i` (a
  Turkish user would expect `ı`), and in the default mode `ı`, `i`, `I` and `İ` all become
  `i`. In case-only mode `ı` stays distinct, `İ` becomes `i` + U+0307 (two symbols) and
  `I` becomes `i`. A Turkic mode is a possible follow-up; it is a per-locale choice that a
  single normaliser cannot make for everyone.
- **Ligatures**: `ﬁ` and its block always expand (both steps do it), `æ` and `œ` only
  expand with diacritic folding (they are letters of their own in Danish and Norwegian).

### 2.3 Limits (documented, not bugs)

- Only ASCII, Latin-1 Supplement, Latin Extended-A, `µ` and U+FB00-U+FB06 are folded.
  Latin Extended-B and Additional (`ș ț ơ ư ẞ` and Vietnamese), Greek, Cyrillic, Armenian,
  Georgian, Cherokee and full-width Latin are **not** case folded or stripped: `Ω` and
  `ω` stay different. Adding them is table work (section 9).
- Only the combining marks U+0300-U+036F are dropped. There is no NFC or NFD: with
  diacritic folding off, a precomposed `é` and `e` + U+0301 are different strings. With it
  on (the default) both become `e`, so decomposed input is handled in the common case.
- The marks are dropped after **any** base character, not only after Latin letters, while
  precomposed letters outside the two blocks are left alone. So the two spellings of a
  letter of another script can come out different: decomposed Cyrillic `й` (`и` + U+0306)
  becomes `и`, but precomposed `й` (U+0439) stays `й`. Vietnamese is affected the same way
  (precomposed `ệ` U+1EC7 is kept, `e` + U+0323 + U+0302 becomes `e`). Normalising the input
  to NFC before indexing avoids the mismatch; the core has no NFC (see above).
- Not folded either (they are outside the tables or not letters): the ordinal indicators `ª`
  and `º`, the superscripts `¹ ² ³`, the no-break space U+00A0 (it is not a space for the
  engine), and capital sharp s `ẞ` (U+1E9E, Latin Extended Additional; lowercase `ß` does
  fold to `ss`).
- No removal of invisible characters (soft hyphen, ZWJ, ZWNJ, bidi marks, BOM): they stay
  symbols and cost an edit if the other side lacks them. Emoji sequences are symbols like
  any other.
- The result depends only on the input and the two flags, never on a locale or a platform.

### 2.4 Source maps

`Normalizer::normalize_mapped(s, &mut SourceMap) -> String` also records, for each output
code point, the index of the input code point it came from. `SourceMap::to_source(range)`
turns a range of output code points into the smallest range of input code points that
covers it, extended over input characters that produced nothing (a dropped combining mark
right after the range belongs to the letter before it). `text::utf8_offset` and
`text::utf16_offset` turn a code-point index of a `&str` into a byte or a UTF-16 unit
offset. This is what #32 needs to report ranges in the caller's original string in all
three units (`text::utf8_range` and `text::utf16_range` do it for a range);
#32 itself (the traceback) is not part of this change.

## 3. The engine alphabet

### 3.1 Symbols are code points, not trie-local ids

The issue asks for "a dense alphabet of code points". Two readings were considered.

- **Trie-local dense ids** (the distinct characters of the dictionary numbered 0..n). The
  cost model would need the code point back for every comparison (neighbour keys), a query
  character absent from the dictionary would need an id that equals no label but still
  equals itself (doubled letters and transpositions compare query characters with each
  other), and ids would differ between tries. It saves nothing on the ASCII path.
- **Scalar values** (a symbol is the `char` as a `u32`). No table between the trie and the
  cost model, ASCII symbols equal the old bytes, and the order of symbols is the order of
  UTF-8 bytes, so sorting and term ids do not change. Chosen.

"Dense" is kept in the sense that each character is one symbol: an edit on `é` is one edit,
as on `e`.

### 3.2 Queries

`Searcher::search(trie, cm, q: &[u8], cfg)` keeps its signature. The bytes are decoded as
UTF-8 into a scratch buffer of symbols that the `Searcher` reuses. A byte that is not part
of a valid UTF-8 sequence becomes the symbol `0x110000 + byte`, above every scalar value, so
it equals no label (terms are `&str`) but equals itself (two identical invalid bytes are
still a doubled letter). Decoding cannot fail and never panics. ASCII bytes are copied as
they are, so for an ASCII query nothing changes.

`search_text` and `search_prefix_text` take a `&str`; if the trie was built with a
normaliser, the query is normalised into another reusable buffer first.

### 3.3 The trie

- Labels are symbols. They are stored in one `Vec<u8>` when every label of the trie is at
  most U+00FF (every ASCII and Latin-1 dictionary, so every dictionary normalised by the
  default normaliser except those with other scripts) and in a `Vec<u32>` otherwise. So
  the memory of an ASCII trie is unchanged; a trie with other scripts pays three bytes
  more per node. The search reads the label through one predictable branch. `Trie::build`
  walks a dictionary whose terms are all ASCII as bytes, as before, and any other one as a
  buffer of code points.
- `len_min`, `len_max` and depths count symbols. For ASCII that is bytes, as before.
- `Trie::label(v)` returns a `char` instead of a `u8` (breaking, see section 6).
- Term order is byte order of UTF-8, which equals code-point order, so term ids,
  `input_index` and duplicate merging are unchanged. With `build_normalized`, duplicates
  are detected after normalisation (`Café` and `cafe` are one term); the entry kept is the
  one with the highest weight, the first among equal weights, and `input_index` points to
  it in the caller's slice, which is how the caller finds its original spelling.
  `Trie::term(id)` returns the normalised text.

### 3.4 Limits: bytes or code points

| limit | unit | why |
| --- | --- | --- |
| term length, `BuildError::TermTooLong` | bytes, at most 65535, of the term as stored (after normalisation) | unchanged; a term has at most as many code points as bytes, so depths still fit `u16` |
| query length, `MAX_QUERY_LEN` = 128, `SearchError::QueryTooLong { len }` | code points (after decoding, and after normalisation for `search_text`) | the DP works per symbol; for ASCII it is the old limit. `len` is counted without storing more than 129 symbols |
| band, budget | symbols | unchanged |

A normalised term that is empty (for example a lone combining mark) is `BuildError::EmptyTerm`.

## 4. The subtree bound with a larger alphabet

`below_mask` and the query masks now use `cost::symbol_class(s: u32) -> u64`:

- `s < 128`: `1 << (s & 63)`, exactly the old `class(b)`;
- `s >= 128`: one of the 38 classes that `a`-`z` (classes 33 to 58) never use, chosen as
  `FREE[s % 38]`, with `FREE` = 0..=32 and 59..=63.

`class(b: u8)` stays and equals `symbol_class(b as u32)` (for bytes 128 to 255 its value
changes: they are Latin-1 code points now, never UTF-8 bytes).

**Admissibility.** The proof of `T_let <= S` in `lower-bound.md` section 3 uses one fact
about classes: equal symbols have equal classes. Any function of the symbol has that
property, so the theorem holds unchanged over the larger alphabet. Collisions (two
different symbols with one class, unavoidable with 64 classes) only make a class look
present in `below_mask` or merge two query classes into one; both shrink the set of
missing classes, so they lower `T_let`, never raise it. The length term `T_comp` counts
symbols on both sides (depths and query positions are symbols), so it is the same
argument with "byte" read as "symbol". The row lemma and the band lemma never looked at
what a symbol is. Section 3a (the sum) is not affected: it is not used.

Why not `s & 63` for everything: the Latin-1 letters `à`-`ÿ` (U+00E0-U+00FF) would land on
the classes of `a`-`z` and `é` would share the class of `i`, so a query `vie` against a
subtree with `é` would lose the missing-`i` term. Keeping the non-ASCII symbols off the
letter classes costs nothing on the ASCII path (the mask is built once per query and once
per trie) and keeps the bound as strong as before on ASCII-heavy text. What it gives on
non-Latin text is not measured; it is a bound, not a result.

## 5. The cost model and the layouts

- `sub_cost` becomes generic over `S: Into<u32>`, `ins_cost` and `del_cost` over
  `S: PartialEq`, so `cm.sub_cost(b'a', b's', 1)` still compiles and returns what it did,
  and `cm.sub_cost('ç', 'l', 1)` works. A `u8` argument is read as the code point U+0000
  to U+00FF.
- Neighbours: the 26x26 bit table for `a`-`z` stays (it is the fast path and it is
  identical to before for every layout). Pairs with a key outside `a`-`z` are kept in a
  short list per layout, computed at compile time from the same geometry. `CostModel::qwerty()`
  has an empty list, so its behaviour is unchanged for every input.
- New active pairs: ABNT2 `ç`-`l`, `ç`-`p`, `ç`-`.`, `ç`-`;` and its punctuation keys
  (`,` `.` `;`), Dvorak `'` `,` `.` `;`, Colemak `;`; AZERTY gains `ù` (next to `m`), QWERTZ
  gains `ü` (after `p`), `ö` and `ä` (after `l`). The geometry rule is unchanged and every
  new key is on a modelled row, so no `a`-`z` pair changes for any layout.
- Every other character (digits, other scripts, uppercase if the caller does not fold) gets
  the default costs: 16 for a substitution, 16 or 8 (doubled) for an insertion or deletion,
  12 for a transposition, all x1.5 on the first query position.
- The minimum costs `c_min`, `c_indel_min` and `c_transpose_min` do not depend on the
  alphabet or the layout, so the band and both bounds are valid for every symbol.

The layout docs lose their "`ç` dropped until #19" caveats.

## 6. Compatibility

What stays exactly as it was (tested):

- For ASCII terms and ASCII queries with `Trie::build` and `search`/`search_prefix`: hits,
  costs, order, term ids, `input_index`, node counts, `below_mask`, `Stats`. The oracle
  tests run unchanged, and a regression test pins trie shape and stats against values
  recorded before the change.
- `CostModel::qwerty()` for every input.

What changes (0.x, listed in the changelog as breaking or behaviour changes):

- **Breaking**: `Trie::label(v)` returns `char`, not `u8`.
- Non-ASCII terms and queries passed to `build` and `search` are compared per code point,
  not per byte (`é` against `e` is one substitution, not two edits). Costs of such queries
  change; that is the point of the change.
- `SearchError::QueryTooLong::len` and `MAX_QUERY_LEN` count code points. For ASCII
  nothing changes; a query of 129 to 512 bytes of non-ASCII text that was refused may now
  be accepted.
- `cost::class` for bytes 128 to 255.
- `CostModel::for_layout` for ABNT2, AZERTY, QWERTZ, Dvorak and Colemak on pairs that
  involve a key outside `a`-`z` (a query with `,` against a term with `o` on Dvorak is now
  a neighbouring-key substitution). `CostModel::for_layout(Layout::Abnt2)` no longer equals
  `CostModel::qwerty()`.
- `CostModel::sub_cost`, `ins_cost` and `del_cost` are generic; an untyped integer literal
  argument (`sub_cost(97, 98, 1)`) no longer infers and needs a suffix.

Additive: the `text` module, `Trie::build_normalized`, `Trie::normalizer`,
`Searcher::search_text`, `Searcher::search_prefix_text`, `cost::symbol_class`,
`BuildError` keeps its variants.

## 7. Performance on the ASCII path

The hot loop gains a branch on the label storage and reads query symbols as `u32` instead
of `u8`; the cost functions take `u32`. The node counts cannot change (same bounds, same
order, section 6), so the check is: node counts and hits identical to `main` on the M0
harness data, then latency on a quiet machine, run last, with the machine load disclosed.
The results are in `docs/benchmarks/unicode.md`.

## 8. Bindings

No binding code was changed with the core (issue #19). The bindings use it since issue #67:

- **WebAssembly and Node** (Node is JavaScript over the wasm build): terms are built with
  `Trie::build_normalized` and queries searched with `search_text`, default normaliser, so
  `sao paulo` finds `São Paulo` and `ACAO` finds `ação`. Hits return the caller's original
  text (through `Trie::input_index`), not the normalised form. The wasm module has no option
  for the mode; the size gate held (18 155 to 19 559 bytes gzip, budget 20 480).
- **C** (`keyhammer-c`): same, with `kh_index_build_ex` flags to turn the case or the diacritic
  folding off. `KH_MAX_QUERY_LEN` counts code points after normalisation (the core's limit),
  with a new `KH_MAX_QUERY_BYTES` (512) bound before decoding; `kh_hit.term` is the original text
  and `kh_hit` gained `input_index`, so the ABI version is 2 (`docs/design/c-abi.md`).
- **Python**: the non-ASCII refusal is lifted; `Index(items, fold_case=True,
  fold_diacritics=True)`; `Hit.term` is the original text and `Hit.index` the input position.

Terms that are equal after normalisation are merged (highest weight, then first) in every
binding. The bindings' tests read the same dictionary, queries and expected hits
(`bindings/testdata`), whose expected file is produced by the core and checked for freshness
by `cargo test -p keyhammer-c`.

## 9. Testing

- `text`: idempotence and determinism over every scalar value and all four modes; the case
  table against `core`'s `char::to_lowercase`; spot checks for every policy row above;
  output of the default mode is ASCII for every letter of the two blocks; source maps and
  offsets against brute force; a `normalize` fuzz target (arbitrary `&str`: combining
  marks, ZWJ, RTL, emoji, NUL) and its deterministic twin in `tests/fuzz_like.rs`.
- Engine: the brute-force oracle (`tests/support`) works on symbols; `tests/oracle.rs`,
  `tests/fuzz_props` and the unit tests of `search.rs` add non-ASCII alphabets (`é ç ã ß æ`
  and non-Latin letters, including colliding classes), with and without normalisation
  applied to both the oracle's input and the engine's.
- ASCII regression: exact trie shape and `Stats` pinned for fixed dictionaries and queries.

As run: the unit tests of `search.rs` check the bound on four non-ASCII alphabets
(`aeéèçß`, `aàĆc` with colliding classes, `жзaЖ😀` with wide labels, `çlp.;` with the ABNT2
neighbours), 43 200 cases per mode as for ASCII: 1 387 728 nodes, 218 100 of them with a
within-budget term below, and 391 968 terminals per mode. Fourteen mutations of the new code
(a case or base table entry, keeping combining marks, case before diacritics, `below_mask` from
the low byte of wide labels, narrow labels up to U+07FF, one symbol for every invalid byte,
ignoring the layout pairs outside `a`-`z`, source ranges not extended, UTF-16 offsets in bytes,
`search_text` not normalising, non-ASCII classes on the letter classes, cross-row layout pairs
dropped, ligatures not case folded) each make at least one test fail; the class mutation, which
only weakens the bound and is admissible, is caught only by the example in the `symbol_class`
docs. Measurements: `docs/benchmarks/unicode.md`.
- Mutation testing of the new tests (a table entry changed, the class function changed,
  decoding changed): each must make a test fail.
