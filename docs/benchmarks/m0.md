# M0 gate (G0) results, 2026-09-23 (branch `m0/prototype`, harness run on 2026-09-23)

## Summary

G0 is a PARTIAL PASS: speed passes, ranking quality does not.

- Oracle equality (exact top-k identical to brute force, both TSB modes): PASS. `cargo test -p keyhammer` is green.
- Latency: PASS. At 274137 words, p95 of the best new mode (new+tsb) is 123.0x lower than the legacy engine (need at least 10x).
- Ranking (MRR of the best new mode at least the baseline "unit edit distance <= 2, then higher weight, then id"): FAIL. 0.389 vs 0.433 at 274137 words, 0.442 vs 0.474 at 100000, 0.526 vs 0.533 at 10000. It fails at every dictionary size and the gap grows with size.

## TSB effect

Real typo data (the 300 Birkbeck pairs, from the harness): TSB expands about 33-35% fewer trie nodes per query, with identical MRR and R@1, and lower p50 and p95 latency.

| Dictionary | nodes/query new | nodes/query new+tsb | Reduction |
|---|---|---|---|
| 10000 | 731 | 489 | 33.1% |
| 100000 | 1385 | 907 | 34.5% |
| 274137 | 1486 | 986 | 33.6% |

The design hypothesis was at least 30% fewer nodes; it holds on this data.

Separate and informational, from different data: a unit test on 200 RANDOM queries against a 2000-word RANDOM dictionary pushed 88526 queue entries without TSB vs 58014 with it (34.5% fewer, identical hits). This is a count of queue entries, not of expanded nodes, and it is not from the typo corpus.

## Why the ranking may lose (hypotheses)

These are UNTESTED HYPOTHESES, not findings.

1. The new engine uses weighted costs (neighbouring-key substitution 8 vs 16, doubled-letter edits 8, transposition 12, first-position multiplier 1.5, unit costs 16). If costs mostly do not tie, so the frequency weight only breaks rare exact ties. The baseline uses integer edit counts, so many candidates tie and frequency decides.
2. The QWERTY-adjacency prior may not match the human errors in this corpus. The Birkbeck corpus may contain many spelling and phonetic errors, not only finger slips.

Suggested next experiments (not run):

- Bucket the cost to whole edits (`ceil(cost/16)`) before applying weight.
- A blended ranking `cost - lambda*weight`.
- A run with all costs set to unit, to check that the engine then reproduces the baseline MRR (a sanity check of the ranking path).

## Caveats

- One machine, one run; latencies vary from run to run. MRR, R@1 and nodes/query are deterministic by construction (no randomness in either engine or the data files); only one run was made.
- 300 typo pairs from the Birkbeck corpus; dictionary of English words, a-z only.
- Costs are provisional; there was no calibration.
- Final tie-break ids differ between engines: the new engine uses byte-sorted term order, the baseline uses the row index in the shuffled words file. Many words have weight 0, so ties among them are broken alphabetically in one engine and randomly in the other. We expect this to be noise rather than a systematic bias; this was not measured.
- The baseline latency is inflated (its edit-distance routine allocates a matrix per candidate) and is not gated.
- The harness has no warm-up.
- Rust-only numbers, with no JS binding overhead.
- The legacy row is the previous engine (`keyhammer-legacy`) with max edit distance 2.

## Prior art

See `docs/papers.md`. Every ingredient of the TSB is already published; only the combination was not found in the works read. The search was limited, so this is not a claim of novelty.

## Verdict and next step

G0 applies as a partial pass: speed is well beyond the gate and the TSB reduces work as hypothesised, but ranking quality is below the baseline at every size. The options are: G0 passed, plan F1; G0 partial (speed ok, MRR below baseline), adjust costs or ranking and repeat M0 before F1; G0 failed, rethink the approach. The suggested next step, which the author may reject, is the partial branch: run the experiments listed above and repeat M0 before F1.
